===== mode room: G does a MeasureOverride that returns nothing move anything? =====
Run twice against the two builds of FluentTeachingTip, same probe, same machine. The committed
spike/TeachingTipProbe/teachingtip-probe-room.txt holds build 1's run (the shipped one); the override was then
installed, the mode re-run, and the control built again without it.

build 1 - no override (base ContentControl.MeasureOverride):
  closed: tip desired 0x0 actual 500x0 | below x=0 y=20 | stack x=103.14 y=216
  open:   tip desired 0x0 actual 500x0 | below x=0 y=20
  re-opened with a target: tip desired 0x0 actual 500x0 | below x=0 y=20

build 2 - override present, returning new Size():
  closed: tip desired 0x0 actual 500x0 | below x=0 y=20 | stack x=103.14 y=216
  open:   tip desired 0x0 actual 500x0 | below x=0 y=20
  re-opened with a target: tip desired 0x0 actual 500x0 | below x=0 y=20

Identical in every column. A Popup that roots a template contributes 0x0 to its host whether it is closed or
showing a card, so the override was dead code and is not in the shipped control. The same A/B ran through the
xunit fact A_tip_holds_no_layout_room_and_still_realizes_its_card, which passed against both builds for the same
reason; it stays in the suite as a guard on the template's root, not as proof of a fix.


===== mode parent: H how the control finds its own window =====
The structural gate AstraGateTests.Theme_kernel_stays_free_of_repair_loops_and_reflection keeps a render-tree
walk out of product code, so the fit check that decides whether a side has room needs another route.

=== H. reaching the host window from inside a control ===
  FrameworkElement.Parent: FluentTeachingTip < Grid < StackPanel < Window
  Application.Current.MainWindow: Window
  same instance as the shown window: True
  tip is inside MainWindow.Content: True

The logical chain reaches the window, so FindWindow walks FrameworkElement.Parent. MainWindow is recorded as an
alternative that would have been wrong: it names one window for the whole app, so in a second-window scenario it
would clip the card against the wrong bounds, while the parent chain follows whichever window hosts the tip.
