  set Border.CornerRadius=3 -> ok
    surface now reads radius=3,3,3,3 LOCAL
    after clearing: radius=0,0,0,0
  set Border.CornerRadius=0 (explicit) -> ok
    surface now reads radius=0,0,0,0 LOCAL, control effective=8,8,8,8

  The fix is the difference between these two blocks: the only line that changed on its own is the radius
  the surface wears at open - 14 before, 8 after - and clearing a local value now returns 8 (our style
  value) where it returned 14 before. Nothing else in the rig moved.

  Contract that fits every reading (the mechanism inside the framework is not readable from here):
    - ContextMenu is the only menu type on the chain that has a CornerRadius at all; MenuFlyout, FlyoutBase,
      Popup and PopupRoot have none, so a style setter on the control is the only input this surface takes.
    - The framework stamps the popup's outer Border with Background / BorderBrush / BorderThickness /
      CornerRadius as LOCAL values, and re-stamps it live when the control's value changes (3 moved it,
      clearing moved it back to the style value).
    - The stamp is a *copy of a value the control was told to take*, not of "any effective value": an unset
      control left the surface on the framework's own 14 pre-fix, while an explicit 0 on the control does
      reach the surface (0,0,0,0 LOCAL). So 0 is a real request, and "no request at all" is what falls back
      to 14. That is why the only way to get upstream's 8 is to write it on the control.
    - Writing the radius on the Border itself is not a route: clearing it drops the surface to 0, because
      the Border's own default is 0 and there is no style behind it.

E. corner of the same card at 8 and at 14, read out of real frames (spike/VisualQA/corner-edge.ps1)
------------------------------------------------------------------------------------------------
spike/FlyoutSurfaceProbe/capture-context.ps1 -Mode context / -Mode context14 holds the menu open and
PrintWindows the probe's own window; context14 opens the menu and then sets the control back to 14
(the pre-fix state) so the frames differ in exactly one input. Read-backs of the two modes:

  context     : surface ... radius=8,8,8,8 LOCAL   (flyout-surface-context.txt)
  context14   : overriding the control radius back to 14 (the pre-fix state): ok
                surface now: 74.27x70 at 200,200.818 radius=14,14,14,14 LOCAL   (flyout-surface-context14.txt)

Three runs, same card, same place in the window. `inset` = how far the first non-background column of that
row sits from the body's left edge; the background (#1C1C1E) is what makes the OUTER edge of the card
legible, stroke and anti-aliasing included:

  out/out-context-...png      radius 8   card top=352 left=350 right=479 width=130 px
    dy=0 inset=12  dy=1 inset=8  dy=2 inset=6  dy=3 inset=5  dy=4 inset=4  dy=5 inset=3
    dy=6 inset=2   dy=8 inset=1   dy=10 inset=0
  out/context-...png          radius 8, RE-CAPTURE of the same mode
    dy=0 inset=9   dy=1 inset=7   dy=2 inset=6  dy=3 inset=4  dy=4 inset=3  dy=6 inset=2
    dy=7 inset=1   dy=9 inset=0
  out/out-context14-...png    radius 14
    dy=0 inset=14  dy=1 inset=12  dy=2 inset=10 dy=3 inset=9  dy=4 inset=8  dy=5 inset=7
    dy=6 inset=6   dy=7 inset=5   dy=8 inset=4  dy=10 inset=3 dy=11 inset=2 dy=14 inset=1
    dy=17 inset=0

  What that says, and what it does not:
    - The 130 px body (74.27 DIP x 1.75) and the body edges (350..479) are identical in all three, so
      nothing but the corner moved.
    - The stable statistic is the DEPTH of the arc: 9-10 rows at radius 8 in both captures of that mode,
      17 rows at radius 14. The corner really is about twice as deep when the surface carries 14.
    - The top row's inset is NOT stable: re-capturing mode `context` with the same radius 8 moved it from
      12 to 9 - a 3 px swing. The popup lands at 201.486 DIP in one run and 200.818 in another (see the two
      read-back lines), and the first non-background column of row 0 depends on where the edge falls inside
      a pixel. So the "12 against 14" reading is inside its own noise and is not used as evidence anywhere;
      it is printed here because it was measured, not because it means something.
    - Absolute radius calibration is also not available from these frames: 8 DIP at 175% should be a 14 px
      arc and the depth reads 9-10, while 14 DIP should be 24.5 and it reads 17. Both are short of
      radius x 1.75, so the frames are a difference-proof and not a ruler; the value the surface carries is
      proven by row C's read-back. Whether the renderer draws arcs short, or this measure of "first
      non-background column" eats a couple of pixels, needs a cross-DPI or cross-radius control that this
      machine (one monitor, 175%) cannot give. Recorded as an open question, not resolved here.

F. the test-host limit this batch ran into (mode context inside xunit)
------------------------------------------------------------------------------------------------
The shared xunit host cannot give a grafted popup a size: the same Open() that yields a 74.27x70 surface
in a window the probe shows itself yields a 0x0 surface under PixelHarness, so PixelAt throws "has no
layout to sample". The corner test in AstraMenuTests therefore asserts the copy contract (which is what a
host can observe) and the arc is evidenced from frames above. Recorded instead of quietly dropped: an
assertion about a pixel this harness cannot reach is not available yet.
