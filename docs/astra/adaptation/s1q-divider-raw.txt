DividerProbe raw transcript - 2026-09-21, Jalium.UI 26.10.9, RenderingEngine.Impeller, 96 DPI render targets.
Built by spike/DividerProbe (Program.cs); run as `dotnet run --project spike/DividerProbe -c Release -- <mode>`.
Every line below is copied out of the tool's own log file, unedited; the two blocks are the two runs that were made.

What the run was for: WinUI has no Divider control at the pinned commit, so the segment had to find its host and its
authority by measurement. The readings that changed a decision are marked at the bottom of this header.

1. Three cells that asked for the token through {ThemeResource} inside a standalone XamlReader.Parse element printed
   nothing (TokenLineLight in mode ink, the mode alpha block, Border1Token in mode shape). Two of those three are
   confounded - they are 1 DIP Rectangles, which print nothing whatever the brush is - but Border1Token is a Border,
   so the markup scope is a real cause. mode shape's last block re-measured it by resolving the brush in code from
   Application.Current and handing it over: 600 ink, the line rows reading #F8F8F8 in Light. Only that second reading
   is evidence about paint, and it is also what shows a {ThemeResource} row is not resolvable from a parsed-but-
   unmerged snippet (the S1-p negative-reading trap, met a second time).
2. "no ink" for a 1 DIP Rectangle survived three alignments and a stroked variant, and a 4 DIP Rectangle
   printed - so the claim in the docs is about the 1 DIP band, not about the shape type.
3. The vertical block prints one line per row on purpose: the row profile is what shows a 1 DIP column landing on
   two columns of pixels.
