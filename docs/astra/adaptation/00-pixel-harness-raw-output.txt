Light, native Button "astra" ............................ #000000 x54176  #F5F5F7 x9680  #1D1D1F x30  #5B5B5D x19  #B7B7B9 x19
Dark,  native Button "astra" ............................ #000000 x54176  #1C1C1E x9680  #FFFFFF x30  #BEBEBF x19  #5D5D5E x19

The 9680 px region is 220 x 44 - the Button's own bounds - and it flips Light #F5F5F7 -> Dark #1C1C1E
with the theme. Neither value appears anywhere in Light.jalxaml or Dark.jalxaml, so that region is
painted by Jalium's default surface, not by an Astra token.

--- attribution probe: does an Astra token drive those pixels? ---
OverrideBrush("ControlFillColorDefaultBrush", #FF00FF) .. magenta pixels = 0, top colours unchanged
then OverrideBrush(..., null) restore ................... top colours unchanged again
Set local Background = #FF00FF on the same Button ....... magenta pixels = 0

So within this capture path neither the palette token nor a local property value reaches the Button's
pixels. Two readings remain open and stage 2 has to separate them:
  (i) the implicit <Style TargetType="Button"> never applies to a native control, or
  (ii) the capture happens before the style/template applies, and only the window's own surface is
      painted by then - which would also explain the empty path-A captures.
The Gallery renders as Astra, so (ii) is the more likely of the two, but it is unproven: it needs a
capture taken after a dispatcher/layout tick, or a capture of the Gallery's own live window.
