# What each section decides:
# [0]  The instrument is live. Both OS settings are on, so a "no animation" reading anywhere below is a claim about
#      the row and not about the machine - and on a machine where either is off, the framework starts no automatic
#      transition at all, which is why the suite never asserts that an animation runs (see [4]).
# [1]  TransitionDuration is a Duration DP registered on UIElement, so it is on every element and not only on
#      Controls; the framework default is 180ms. The three states are distinguishable from the value alone
#      (Automatic vs 0ms), which is what makes a dropped row detectable. DurationConverter takes both time forms and
#      "0", and throws on "Auto" - so an "Auto" row would be a parse failure, not a clear.
# [2]  The row type is the whole story: only <Duration> written unqualified under the framework's own xmlns produces
#      a Duration object, and it then lands through all four consumer shapes - including inside a ControlTemplate.
#      Upstream's <x:String> shape stores the text and hands the consumer 180ms in all four shapes: silently, with no
#      parse error. <sys:TimeSpan> is worse: the row itself loses the fraction ("00:00:00.083" stores as "00:00:00"),
#      so a TimeSpan row is both a truncated number and an unlanded one. The two clr-namespace spellings of Duration
#      cannot be resolved at all, from either assembly name, and x:Double cannot be resolved in the x: namespace - the
#      same shape the styles files already document for the metric rows.
# [3]/[3b] A write to the live row re-resolves within four pumped frames, on a bare element and on a Border inside a
#      realised ControlTemplate, with no theme re-apply needed. This is the mechanism ReduceMotion uses.
# [4]  The lever moves something. 400ms from red to blue reads an in-between #DB0093 off the property and 1600 of
#      1600 ink pixels in-between; the same row written as 400ms through {ThemeResource} reads #DC0091 and 1600
#      in-between; the same row flipped to zero reads the asked-for #0000FF with 1600 end-like pixels and no ink
#      between - i.e. nothing animated. Positive and negative controls in one run, so neither reading is explained by
#      the judge.
