[G4] The finding that changes the design: zero-rect arrange does not hide a sized child
  Upstream hides a collapsed crumb with Arrange(new Rect(0,0,0,0)) and never touches Visibility
  (BreadcrumbLayout.cpp:89-93). Copied literally onto this runtime, with four Borders of Width=100 Height=40 in a
  250-wide panel (so the rule zero-rects the third and fourth):
      child[0] Border actual=100x40 at=(0,0)      <- red
      child[1] Border actual=100x40 at=(100,0)    <- lime
      child[2] Border actual=100x40 at=(0,0)      <- blue,   zero-rected, still 100x40, now at the origin
      child[3] Border actual=100x40 at=(0,0)      <- yellow, zero-rected, still 100x40, now at the origin
      capture 250x40: red 0 px, lime 4000 px, blue 0 px, yellow 4000 px, black 2000 px
  The arranged rect sets the OFFSET but not the extent: an element carrying its own Width/Height keeps that size
  inside a 0x0 slot and stacks at the panel origin. The three "hidden" boxes all pile up at (0,0) and the
  last-drawn one (yellow) is what paints there. So the histogram is exactly what an unhidden overlap looks like:
  0..100 yellow, 100..200 lime, 200..250 nothing.
  A width-less child behaves differently - in pass B the six TextBlock crumbs that were zero-rected did report
  actual=0x0 - because with no local size the framework re-measured them into the zero slot. That is the case
  upstream lives in (a crumb is a ContentPresenter sized to its content) and it is NOT the case a crumb with a
  template's own MinWidth/Padding lands in.
  Consequence for this layer: the collapse must go through Visibility=Collapsed (or by not realizing the crumb),
  not through a zero rect. Recording it before writing the panel, because a zero-rect port would have produced a
  bar whose hidden crumbs pile up under the visible first crumb - painted, hit-testable, and invisible only to
  whoever reads ActualWidth.

[G5] The replacement mechanism, measured the same way
  Same four 100x40 solid Borders in a 250-wide panel, same rule (the third and fourth are hidden), only the
  mechanism changes to Visibility=Collapsed:
      child[0] Border actual=100x40 at=(0,0)
      child[1] Border actual=100x40 at=(100,0)
      child[2] Border actual=0x0    at=(0,0)
      child[3] Border actual=0x0    at=(0,0)
      capture 250x40: red 4000 px, lime 4000 px, blue 0 px, yellow 0 px, black 2000 px
      histogram: FF0000x4000 00FF00x4000 000000x2000
  Both the geometry read-back and the capture agree, which is the pair this branch requires: a mechanism is only a
  hiding mechanism if the pixels say so too. So FluentBreadcrumbBar's collapse panel takes the same greedy
  right-to-left fit and the same floor (ellipsis + last crumb always visible) as upstream's BreadcrumbLayout, and
  implements the "shrink to nothing" of BreadcrumbLayout.cpp:89-93 as Collapsed.
  What is deliberately NOT claimed: that a zero rect never hides anything. Pass B (six width-less TextBlock crumbs
  inside a real ItemsControl) did read actual=0x0 after zero-rect arrange, so the upstream mechanism works for a
  container that carries no size of its own. It is this layer's templates that put MinWidth/Padding on the crumb
  root, and once they do, the zero rect stops being a hide. If a future change makes the crumb root size-free, the
  question is open again - and pass C is the experiment that answers it.

[G6] A ContentControl-derived own type does not expand its own template until it opts in
  symptom: the behaviour tests read "No PART_ItemButton under FluentBreadcrumbBarItem" while the resource lookups
  were all green. What the probe (spike/BreadcrumbProbe mode style) measured instead:
      TryFindResource(DefaultBreadcrumbBarItemStyle) => Style
      implicit style for FluentBreadcrumbBarItem     => Style
      crumb.Style=<null> crumb.Template=ControlTemplate  template.LoadContent() => Grid, children=3
      realized crumb's only visual child             => TextBlock 59.75x19.78
  So the style is found, the Template property is set, the template itself materialises on demand - and the realized
  control still paints its bare content. The missing line is ContentControl's protected UseTemplateContentManagement(),
  which every ContentControl-derived own type in this layer already calls (FluentTabViewItem.cs:77, FluentInfoBar.cs:51,
  FluentNavigationView.cs:53, FluentTeachingTip.cs:161), together with DefaultStyleKey = typeof(itself). With both,
  the same crumb walks out as Grid 81.75x36 > {Button PART_ItemButton 63.75x36, PART_LastItemContentPresenter 0x0,
  TextBlock PART_ChevronTextBlock 18x14}.
  Why the obvious reading is wrong: the layer's ApplyDefaultStyle fallback (FluentDropDownButton/FluentRadioButtons)
  never runs for these types, because "Style is already set" is true from the start - the framework's own
  ContentControl default is in that slot. A fallback that keys off Style being null cannot see the difference
  between "the application chose" and "nobody chose"; DefaultStyleKey is the only route that wins.

[G7] A collapsed container leaves the items panel's Children, and the row must be judged against the bar's width
  Two readings from mode narrow, both after the control looked correct at 600:
      width=260 measured=225.25 (three of four crumbs) arranged=200 first=0
      after switching the hide to Hidden: measured=307 arranged=200 against=260 first=2
  (a) Visibility=Collapsed removes the container from Panel.Children, so the NEXT measure pass no longer sees the
      crumb it just hid: the sum falls, "does it fit" flips to yes, and the row reports no overflow while the
      crumb is still not arranged. Hidden keeps the element in Children and keeps its DesiredSize; the arrange walk
      is what declines to give it a place. The ink claim is unchanged - the capture of a Hidden crumb holds 0 pixels
      of its sentinel, which is the arm the A/B in the tests locks down.
  (b) The fit cannot compare against finalSize.Width, because that number is the presenter's column, and the column
      is what showing the ellipsis changes. It compares against the host bar's own width (FluentBreadcrumbBar.RowWidth),
      which the app gave and nothing inside the control disturbs. The ellipsis's measured 60 DIP is then reserved out
      of that width, and showing it invalidates measure once so the reservation uses a real number instead of the 0 a
      collapsed element reports.
